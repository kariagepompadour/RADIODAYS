# 時計の現地時刻化と、太陽・月の昼夜判定：調査と設計提案

- 作成日：2026-10-22
- 状態：**作者が承認し、U7で実装**（[usb-u7.md](usb-u7.md)）。WORLDは日本時間、タイムゾーン名・時差は表示しない
- 調べた版：U6（時計と空の処理はU4・U5・U6で同じ。比較で確認）

## 1. 調査の結果（要約）

| 確認事項 | 今の作り（U4〜U6） | 希望の仕様との差 |
| --- | --- | --- |
| 各Locationのタイムゾーン | **ない**。Locationにあるのは名前、都市名、緯度・経度だけ | 足りない |
| 時計の表示 | **常に日本時間**（`CLOCK_TZ = "JST-9"`、固定）。Stage 2-5から「Locationに関係なく日本時間」という**決めた仕様**で、不具合ではない | 選んだ都市の現地時刻にしたい → 変更が必要 |
| Location変更時の時計 | 画面全体を描き直すので、時計もすぐ描き直される。ただし時刻は日本時間のまま | 現地時刻にすれば、そのまま直ちに切り替わる |
| 夏時間 | 対応していない（日本時間だけなので不要だった） | 必要 |
| 時差による日付 | 日付も日本時間 | 現地の日付にすれば、時刻と同じ仕組みで切り替わる |
| 太陽と月の切り替え | **すでに希望の仕様どおり**：選んだ都市の緯度・経度とUTCから太陽の高度を計算し、−0.833°（日の出・日の入りの定義）より上なら太陽、下なら月 | 差はない（第3節） |
| Location変更時の太陽・月 | 都市が変わると、その場で計算し直して描き直す | 差はない |
| 季節の変化 | 太陽の赤緯を毎回計算しているので反映される | 差はない |

## 2. 今の時計の仕組み

- 時刻のもと：SNTP（Wi-Fi）か、USB中継のUTCの秒（U3から）。どちらもシステムの時計をUTCで合わせる
- 表示：`drawClock()` が `localtime_r()` でUTCを地方時に直す。地方時は環境変数 `TZ` で決まり、`clockInit()`（起動時）と `clockService()`（SNTPを始めるとき）で `"JST-9"` に設定している。**Locationを替えても `TZ` は変わらない**
- 描き直し：日付と「時:分」は1分ごと、コロンは1秒ごと。Locationを替えると画面全体を描き直すので、時計もすぐ描かれる

## 3. 今の太陽・月の判定（検証済み）

- `updateSky()`：都市の緯度・経度（WORLDは東京）とUTCで `solarAltitudeDeg()` を計算し、高度が −0.833°（大気の屈折と太陽の半径を含む、日の出・日の入りの標準の定義）より上なら昼。**これは「日の出から日の入りまで太陽」と同じ判定**で、日付・季節・都市の違いは計算の中にすべて入っている
- 計算は1分ごと。**Locationを替えたときはすぐ**に計算し直す
- 精度の確認（Macで、スケッチの計算をそのまま移して、NOAAの太陽計算（Meeusの方法）と比べた）：東京、ロンドン、ニューヨーク、ストックホルム、シドニー、ウェリントン、バンコクの春分・夏至・秋分・冬至で、**日の出・日の入りの差は最大0.2分**
- 同じUTCでも都市ごとに昼夜が違う（例：UTC 00:30は東京が昼、ロンドンとニューヨークは夜）。これは今もそのとおりに表示される
- 切り替えの遅れ：1分ごとの計算なので、日の出・日の入りから最大1分遅れて絵が変わる
- 高緯度：19か所でいちばん北はストックホルム（59.33°N）で、毎日日の出と日の入りがある。高度で判定しているので、白夜（一日中太陽）や極夜（一日中月）の場所でも、特別な処理なしで正しく出る
- 月は満ち欠けを描いている（今のまま。月の出・月の入りは計算しない）

**結論：太陽・月は修正不要。** 変更が必要なのは時計（タイムゾーンと夏時間）だけ。

## 4. 時計の現地時刻化：設計案

### 4.1 方式

POSIX形式のタイムゾーン文字列（夏時間の規則を含む）を各Locationに持たせ、Locationが変わったら `setenv("TZ", …)`・`tzset()` で切り替える。`localtime_r()` が夏時間と日付をそのまま正しく計算する。

- 今も `setenv`・`tzset` を使っているので、使う仕組みは同じ（新しいライブラリやタスク、通信は不要）
- システムの時計はUTCのまま（SNTP、USB中継の時刻、太陽・月の計算は変わらない）

### 4.2 各Locationのタイムゾーン（案）

| Location | 都市 | TZ文字列 | 夏時間 |
| --- | --- | --- | --- |
| JAPAN | 東京 | `JST-9` | なし |
| USA | ニューヨーク | `EST5EDT,M3.2.0,M11.1.0` | 3月第2日曜〜11月第1日曜 |
| UK | ロンドン | `GMT0BST,M3.5.0/1,M10.5.0` | 3月最終日曜〜10月最終日曜 |
| FRANCE、GERMANY、HOLLAND、POLAND、CZECHIA、SWEDEN、ITALY、HUNGARY | 各首都 | `CET-1CEST,M3.5.0,M10.5.0/3` | 同上（中央ヨーロッパ時間） |
| THAI | バンコク | `ICT-7` | なし |
| TAIWAN | 台北 | `CST-8` | なし |
| AUSSIE | シドニー | `AEST-10AEDT,M10.1.0,M4.1.0/3` | 10月第1日曜〜4月第1日曜（南半球） |
| NZ | ウェリントン | `NZST-12NZDT,M9.5.0,M4.1.0/3` | 9月最終日曜〜4月第1日曜（南半球） |
| CANADA | オタワ | `EST5EDT,M3.2.0,M11.1.0` | アメリカと同じ |
| BRAZIL | ブラジリア | `BRT3` | なし（2019年に廃止） |
| ARGENT | ブエノスアイレス | `ART3` | なし |
| WORLD | （都市なし。空は東京） | **作者の判断**：`JST-9`（今と同じ、空の東京と一致）を推奨 | ― |

Macで、このTZ文字列が2026年の夏時間の始まりと終わりの瞬間に正しく切り替わることを確かめた（ニューヨーク 3月8日・11月1日、ロンドンと中央ヨーロッパ 3月29日・10月25日、シドニー 4月5日・10月4日、ウェリントン 4月5日・9月27日）。日付が変わる時刻（東京はUTC 15:00、台北16:00、バンコク17:00、ブラジリア翌日3:00）も正しい。

**注意**：
- 時計は**Locationの都市**の時刻になる（USAはニューヨーク、CANADAはオタワ、AUSSIEはシドニー）。局の所在地（シアトル、カルガリー、アデレードなど）とは時差がある場合がある。空の昼夜もLocationの都市で決めているので、時計と空はそろう
- 夏時間の規則はプログラムに組み込むため、国が制度を変えたら（EUでは廃止の議論がある）更新が必要
- Cardputerの中のCライブラリ（newlib）は同じ形式の文字列に対応している（ESP-IDFの説明にも同じ形式の例がある）。ただし**実機では未確認**。Macの確認は別のCライブラリで行った

### 4.3 直す箇所

| 場所 | 変更 |
| --- | --- |
| `stations.h` の `Location` | `tz` の項目を1つ加え、19か所に文字列を入れる（局名・URL・順番は変えない。保存したLocationとの互換性も変わらない） |
| `clockInit()`（起動時） | `"JST-9"` の代わりに、保存したLocationの `tz` を設定する |
| `applyLocation()`（Locationの切り替え） | 新しいLocationの `tz` を設定し、時計の表示をすぐ描き直す（今も画面全体の描き直しで描かれる） |
| `clockService()`（SNTPを始めるとき） | 今は `configTzTime("JST-9", …)` と `setenv("TZ","JST-9")` で**日本時間に戻してしまう**。ここを今のLocationの `tz` にする（直し忘れると、Wi-Fiで時刻が合った瞬間に日本時間に戻る） |
| `drawClock()` | 変更なし（`localtime_r()` が現地時刻を返すようになる）。コメントの「JST」を直す |
| 太陽・月 | 変更なし |
| シリアルの記録 | Locationの切り替え時に `[CLOCK] zone …, local …` を1行（実機でTZの動作を確かめやすくする。任意） |

画面のデザインは変えない（時差やタイムゾーン名は表示しない）。表示したい場合は別に相談。

| 項目 | 見込み |
| --- | --- |
| TZ文字列（同じ文字列はまとめられるので9種類、約170バイト） | 約0.2 KB |
| `Location` の項目（19か所×4バイト） | 約0.1 KB |

| Cライブラリ | 増えない見込み（`tzset` は今も使っており、夏時間の規則の読み取りも同じ関数の中）【推測】 |

RAMとヒープはほとんど増えない。描画・音声・USB・Wi-Fi・選局の処理には触れない。

## 5. 推奨する実装方針

1. 太陽・月は今のまま（希望の仕様を満たしていることを確認済み）
2. 時計だけを、Locationごとの**POSIXのTZ文字列**で現地時刻にする（第4節）。新しい版（例：U7）として、U6のダイヤルはそのまま
3. WORLDは日本時間（空の東京と一致）
4. 試験
   - Mac：各Locationの文字列で、東京・ロンドン・ニューヨーク・シドニー・ウェリントンの夏時間の始まり・終わりの前後、日付の変わり目、同じUTCでの各都市の時刻（今回の確認を試験にまとめる）
   - Mac：スケッチの `applyLocation()` などを切り出し、Locationを替えると `TZ` が変わり、時計が描き直されること。SNTPの開始で日本時間に戻らないこと
   - 回帰：U6のダイヤルの試験、U4のホスト試験、プレビューとの比較
   - 実機：Locationを替えたときの時計、Wi-FiのSNTPとUSB中継の時刻のどちらでも現地時刻になること、記録の1行
