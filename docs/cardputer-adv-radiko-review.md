## 2. HLS／AACの受信と復号の方式【コード】

```text
認証（HTTPS）→ プレイリスト（m3u8、HTTPS）→ AACのセグメントを順に取得（HTTPS、keep-alive）
   → 圧縮AACの先読みFIFO 28 KB（FreeRTOSのStreamBuffer）
   → 復号のタスク（Helix AAC、SBRなし）→ PCMのリング 5×4,608サンプル → M5のスピーカー（playRaw）
```

| 段階 | 実装 |
| --- | --- |
| 通信 | すべてHTTPS（`WiFiClientSecure`）。radikoの配信網は平文のHTTPを受け付けない（コメント）。**証明書の検証はしていない**（`setInsecure()`） |
| HLS | マスターのm3u8から最後の変種（最も高いビットレート）を選び、チャンクリストを読み、`#EXT-X-MEDIA-SEQUENCE` で新しいセグメントだけを取る。セグメントは `Content-Length` 分だけ読む（keep-alive のため） |
| 形式 | AAC（48 kbps）。HE-AACのSBR（高い音域の復元）は、ビルド前のスクリプト（`disable_sbr.py`）でライブラリの設定を書き換えて**無効**にし、AAC-LCの部分だけを復号（高い音は控えめ。作者の説明） |
| 復号 | arduino-libhelix（`AACDecoderHelix`）を、**静的な32 KBの領域**から確保する派生クラスで使う（ヒープの断片化を避けるため） |
| タスク | 受信 `radiko-net`（スタック12 KB、コア0）、復号 `radiko-dec`（スタック16 KB、コア1）。画面と操作は `loop()` |
| 出力 | 復号したPCMを5個のバッファのリングに入れ、M5のスピーカーへ（コピーしない再生なので、再生中のバッファを上書きしない工夫） |
| 再認証 | 401／403で再認証。1本も再生できない403が続くと「配信対象外」として止まる |
| そのほか | 番組名（radikoの番組表のXML）、日本語の字体（lgfxJapanGothic）、Wi-Fiの設定（WiFiManagerのウェブ画面と本体キーボード）、NTPの時計、電池の表示 |

## 4. RADIO DAYSとの比較

| 項目 | 共通点 | 相違点 |
| --- | --- | --- |
| 機器 | Cardputer ADV、ESP32-S3、PSRAMなし、M5のスピーカー | ― |
| 音声の流れ | 受信と復号を別のタスクにし、バッファで受信の揺れを吸収 | RADIO DAYSはHTTPのMP3（ESP8266Audio）。こちらはHTTPSのHLS／AAC（libhelix）。TLSと、m3u8を繰り返し読む処理がある |
| ライセンス | どちらもGPL v3の音声ライブラリを含むので、**バイナリはGPL v3**（RADIO DAYSは公開前の課題A1） | ― |
| 導入 | ― | こちらは0x0への全体の書き込み（Launcherを上書きする）。RADIO DAYSの約束（Launcher経由、本体へ直接書き込まない）とは合わない |
| 大きさ | 1.37〜1.39 MBで近い | RADIO DAYSは残り1,856 B。HTTPS（TLS）とAACの復号を**加える**と、0x150000に収まらない見込み【推測：TLSとAAC復号のコードで数十KB以上】 |
| 画面 | 時計、Wi-Fiの設定、局の一覧 | RADIO DAYSはダイヤル、地球儀、空など。日本語の字体は持たない |

## 5. radikoの認証方法と利用規約

### 5.1 認証のしかた【コード】

1. radikoの公式のウェブプレーヤーが使う内部のAPI（`auth1`）に、**公式のPC用HTML5プレーヤーを名乗る見出し**（アプリ名 `pc_html5`、利用者 `dummy_user`、機器 `pc`）で接続し、トークンと「鍵の位置」を受け取る
2. **公式プレーヤーに埋め込まれた固定の鍵**（40文字。ソースに書かれている）から指定の部分を切り出して `auth2` に送り、地域（例 JP14）を受け取る
3. そのトークンを付けて、配信網のm3u8とAACのセグメントを取得する

参考にしたのは、第三者の動画・音声取得ツール（streamlink）のradiko用の部品と、radikoのAPIの解説記事【作者】。作者は「APIは年に1回ほど変わる。動かなくなったら認証とURLを更新する」と書いている【作者】。

### 5.2 技術的に実現できるか（技術の評価）

- **できる**：作者は実機で連続再生を確認したとしている【作者】。仕組みは公式のウェブプレーヤーと同じ手順の再現で、地域の判定はサーバー側（接続元のIP）に任せている
- ただし、radikoの内部のAPIや鍵が変われば動かなくなる（公式に公開された仕様ではない）
- 証明書を検証しないので、通信を途中で差し替えられても気づかない（安全上の弱さ）

### 5.3 利用の許可との関係（規約の評価。法的な判断ではない）

| 規約の条文【規約】 | このアプリとの関係 |
| --- | --- |
| 第4条(3)：radikoのソフトウェア、または会社が別に提供する方法以外で聴くことを禁止 | このアプリはradikoのソフトウェアではなく、公式に提供された方法（公式アプリ、ウェブ、対応機器、埋め込みの部品）にも当たらない |
| 第4条(4)：認証の情報の解読、認証の回避の禁止 | 公式プレーヤーの鍵を使って、公式プレーヤーを名乗って認証している。「回避」に当たるかは解釈の問題だが、少なくとも公式の方法ではない |
| 第4条(5)：公式の方法以外での復号、その方法の公開の禁止 | 公式以外のソフトウェアで復号し、その方法をソースとして公開している |
| 第4条(7)：規約を超える利用を可能にする道具の開発の禁止 | 公式以外での聴取を可能にする道具にあたる可能性がある |
| 第3条：私的な聴取、地域の外では聴けない | このアプリは地域の判定をサーバーに任せ、地域の偽装やエリアフリーはしない、録音もしないと作者が書いている。**この点は規約に沿っている** |

**評価**：技術的には実現できているが、公開されている規約の範囲では、**radikoが認めた聴き方に当たらない**と読める（第4条(3)(5)、場合によって(4)(7)）。私的な聴取・地域の内側・録音なしという配慮はあっても、それだけで「公式に認められた方法」にはならない。radikoの許可（対応機器としての契約など）があれば別。

## 6. RADIO DAYSへの意味

| 観点 | 評価 |
| --- | --- |
| radikoをRADIO DAYSに取り入れる | **勧めない**。作者の方針（非公式のAPIやアクセスの制限の回避を前提にしない、正規の方法を優先）と合わない。規約上の問題に加え、内部のAPIの変更で動かなくなる |
| 大きさ | 加えるなら0x150000の決まりを広げる必要がある【推測】 |
| 技術として学べること | radiko以外の、**正規にHTTPS・HLS・AACで配信している局**を将来扱う場合の参考になる：TLSの接続を1本だけkeep-aliveで使い回す、AACの復号の領域を静的に確保して断片化を避ける、SBRを外してメモリを節約する、圧縮データのFIFOとPCMのリングを分ける、など。ただし、その場合も各局の利用条件を確かめる必要がある |
| 導入の形 | 0x0への全体の書き込みは、RADIO DAYSの約束（Launcher経由）と合わない |

## 7. 結論

- Cardputer ADV単独でのradikoの受信は、**技術的には可能であることが示されている**（HTTPS、HLS、AAC-LC、静的な復号の領域、28 KBの先読み、アプリ約1.39 MB、静的RAM約89 KB）
- その認証は、radikoの公式プレーヤーの内部の手順と鍵を再現するもので、radikoのユーザー規約が認める「公式のソフトウェアまたは会社が提供する方法」には当たらないと読める。**技術的な実現性と、利用の許可は別の問題**
- RADIO DAYSとしては、radikoの直接の受信は採用しない（前回の方針どおり保留）。技術の工夫は、将来の正規のHTTPS・AACの局のための参考として記録する
