## 1. KariPomのUSB通信方式の実態

### 1.1 調べたもの

| リポジトリ | 中身 |
| --- | --- |
| `KariPom` | CoreS3のファームウェア（`cores3-main/karipom_cores3/karipom_cores3.ino`、約25,000行）とMac・PC用のCompanion（`mac-companion/karipom_companion.py`、約11,500行、Python・PyQt5） |
| `KariPom-Desktop` | Macだけで動くデスクトップアプリ（Python）。「Arduino・M5Stackなどの専用ハードウェア不要」とREADMEにある【確認】 |
| `KariPom-Web` | ブラウザで動く版（`index.html`） |

### 1.2 わかったこと【確認】

| 項目 | 結果 |
| --- | --- |
| CoreS3とMacの間のデータ | **Wi-Fi経由**。発話状態とFFTの結果を**UDP**（ポート12345）で送り、記録や設定は**HTTP**（ポート80、`WebServer`）で取得する |
| Wi-Fiの使い方 | ① ルーターにつなぐ（STA）、② つながらなければ、**CoreS3が自分でWi-Fiの親機になる（APモード、`192.168.4.1`）**。実際の記録（`karipom_current.log`）にも「AP IP = 192.168.4.1」がある |
| USBの使い方 | **給電と、シリアルへの記録の出力（`Serial.begin(921600)`）だけ。** ファームウェアには、シリアルから読み込む処理（`Serial.read` など）がない |
| Mac側のプログラム | Companion（Python、PyQt5・requestsなどが必要）。シリアル通信のライブラリ（pyserial）は使っていない。通信先はIPアドレス（`karipom_config.json` の `"ip"`）で指定する |
| READMEのUSBの記述 | 給電に関するものだけ |

**結論：今あるKariPomのソースには、USBでデータを送受信する仕組みは見つからなかった。** 「Wi-Fiを使わずにMacとUSBでつないで動いた」構成として考えられるのは、次のどれか【推測】。

1. **KariPom Desktop**：Macだけで動き、機器が要らない
2. **CoreS3のAPモード**：ルーターのWi-Fiは使わないが、CoreS3が自分でWi-Fiを出し、MacがそこへWi-Fiでつながる。USBは給電だけ
3. ここにない別の版

どの構成のことか教えていただければ、その構成を確かめます。

### 1.3 RADIO DAYSに応用できるか

| KariPomの方式 | RADIO DAYSでは |
| --- | --- |
| APモード＋Mac側のプログラム | 職場のMacは有線LANでインターネットにつながり、Wi-Fiは空いているので、MacがCardputerのWi-Fi（AP）につながることはできる【推測】。ただし、Cardputerがインターネットに出るには、**Macが放送を中継するプログラムを動かす必要がある**。macOSには、追加なしで使える中継の仕組みがない（Pythonも標準では入っていない【一般】）。また、職場で独自のWi-Fiを出すこと自体が、規則で禁止されていることが多い |
| UDP・HTTPでの通信 | ネットワークでつながっていれば使えるが、「USBだけ」の解決にはならない |

**→ KariPomの方式をそのまま使っても、「Wi-Fiなし、USBだけ」にはならない。** 再利用できるのは、「Mac側のプログラムが、IPアドレスで指定した機器とやり取りする」という考え方まで。

## 2. 前提の確認

| 項目 | 結果 |
| --- | --- |
| Cardputer ADVのUSB | ESP32-S3のUSB（Full Speed、12 Mbps）。Media JogがこのポートでUSB HIDとして動いている【確認】 |
| RADIO DAYSの今のUSB設定 | Hardware CDC and JTAG（USB-Serial-JTAG）。シリアルの記録に使っている【確認】 |
| シリアルの機能 | `HWCDC` に、受信バッファーの大きさの設定（`setRxBufferSize`）と、ホストにつながっているかの確認（`isConnected`）がある【確認：コア3.3.9の `HWCDC.h`】 |
| 必要な速さ | 128 kbpsのMP3で約16 KB/秒。USBのシリアルの実際の速さ（数百KB/秒以上と言われる【一般】）に比べて十分に小さい |

**ただし、速さが足りることと、途切れずに再生できることは別の問題。** 途切れの原因になるのは、受信の間隔のむら、Mac側の処理の止まり、局を変えるときの切り替え、USBの抜き差しなどで、どれも第3節の設計で扱う。

## 3. USBシリアル中継の実装案（推奨）

### 3.1 全体の流れ

```text
Cardputer                                  Mac（スクリプト）
  起動・USBにつながる
  "@RD HELLO 1"  ───────────────────────▶  ポートを見つけ、合図を確認
                 ◀───────────────────────  "@RDOK 1"（中継できる）
  ダイヤルで選局
  "@RD TUNE 3 http://..." ──────────────▶  前の受信を止め、
                 ◀───────────────────────  "RDSYNC-7\n" ＋ MP3のデータ（curl）
  合図の後のMP3を再生
  "@RD PING"（数秒ごと） ────────────────▶  （生きている確認）
```

### 3.2 決めること

| 課題 | 設計 |
| --- | --- |
| **選局の指示（Cardputer→Mac）** | 1行の文字列。先頭を `@RD ` に決め、記録の行と区別する。例：`@RD TUNE <番号> <URL>`、`@RD STOP`、`@RD PING` |
| **MP3の転送（Mac→Cardputer）** | `curl` の出力をそのままシリアルへ流す（バイナリ）。**シリアルを「raw」にして、改行などを書き換えない**（`stty -f <ポート> raw -echo`）。これを忘れるとMP3が壊れる |
| **双方向** | USBのシリアルは双方向に同時に使える。Cardputer→Macは文字（記録と指示）、Mac→CardputerはMP3、と方向で役割を分ける |
| **音声と制御の分離** | Mac→Cardputer方向には、局が変わるたびに、MP3の前に区切りの文字列 `RDSYNC-<番号>\n` を1回だけ送る。Cardputerは、TUNEを送ってから、自分が待っている番号の区切りが来るまで、届いたデータを捨てる（前の局の残りを再生しない）。MP3の中に同じ12バイトが偶然現れる確率はごく小さい【推測】 |
| **局の変更** | Cardputer：今の再生を止め、TUNEを送り、区切りを待つ。Mac：今の `curl` を止めて区切りを送り、次の `curl` を始める |
| **バッファー** | シリアルの受信バッファーを8〜16 KBにする（`setRxBufferSize`、Launcherも8 KB【確認】）。その先は今の32 KBのストリーム用バッファーとMP3デコーダーをそのまま使う。再生を始める前に、今と同じく3/4まで貯める（約1.5秒） |
| **流れの調整** | Cardputerの受信バッファーがいっぱいになると、USBは送り手を待たせ、Macの書き込み、`curl` の受信の順に自然に遅くなる【一般】。放送局は実時間で送ってくるので、通常は問題にならない【推測】 |
| **記録との干渉** | 記録は今まで通りシリアルに出す（Cardputer→Mac方向）。スクリプトは `@RD ` で始まる行だけを読み、ほかは読み捨てる。記録の出力が止まらない設定（`setTxTimeoutMs(0)`）は今もしている【確認】 |
| **USBの抜き差し** | Cardputer：`isConnected()` がfalseになるか、数秒データが来なければ、中継をやめてWi-Fiへ（または待機）。Mac：書き込みに失敗したら、ポートが現れるまで待つ状態に戻る |
| **Wi-Fiとの切り替え** | 起動時に「中継の返事（`@RDOK`）があればUSB、なければWi-Fi」。画面に「USB」「Wi-Fi」の印を出す。両方あるときにどちらを優先するかは設定にする |
| **曲名** | `curl` は曲名の情報を要求しないので、曲名は出ない（必要なら後で対応） |
| **HTTPSの局** | Macの `curl` が受信するので、HTTPSの局も中継できる。Cardputer単体では聴けない局が増える |
| **局の一覧** | URLはCardputerから送る（一覧は今の `stations.h` だけで済む）。スクリプトは、URLが `http://` か `https://` で始まり、使える文字だけでできていることを確かめ、シェルに解釈させずに1つの引数として `curl` に渡す |
| **Cardputer側の変更** | 「シリアルから読む音声の入口」（`AudioFileSource` を1つ追加）、区切りの検出、HELLO・TUNE・PINGの送受信、USB／Wi-Fiの切り替え、画面の印。デコーダー、スピーカー、ノイズ、メーター、選局、Location、地球儀はそのまま |
| **アプリの大きさ** | USBの設定は今のまま（Hardware CDC and JTAG）なので、増えるのは数KBの見込み【推測】 |

### 3.3 気をつけること（技術的な問題）

| 問題 | 内容 | 対策 |
| --- | --- | --- |
| **ポートを開いたときにリセットされる可能性** | USB-Serial-JTAGは、ホストの制御信号（DTR・RTS）の組み合わせで本体をリセットする仕組みがある【一般】。Macでポートを開いたときにリセットされると、Launcherから起動し直すことになる | `stty -f <ポート> -hupcl` などで制御信号を変えない。**【要実機】最初に必ず確かめる** |
| raw設定 | 改行の変換などが残るとMP3が壊れる | `stty raw -echo` をスクリプトの最初に設定する |
| 別のシリアル機器 | 間違えて別の機器にデータを送らない | スクリプトは、まず読むだけで `@RD HELLO` を待ち、それが来たポートにだけ書き込む |
| Macのスリープ | スリープするとUSBが止まり、音が切れる | スクリプトの実行中は `caffeinate -i` でスリープを防ぐ（標準のコマンド【一般】） |
| 社内プロキシ | プロキシ経由でしか外に出られない場合 | `curl` にプロキシを指定する（`https_proxy` などの設定。macOSのシステム設定のプロキシは自動では使わない【一般】）。社内のHTTPS検査では、会社の証明書がMacに入っていれば `curl` も使える見込み【推測】 |
| ポート番号 | 多くの局が8000などで配信していて、防火壁で遮断される可能性がある | 職場のネットワークで、まず `curl` で受信できるかを試す |
| Gatekeeper | ダウンロードしたスクリプトは、初回に警告が出る | 右クリック→「開く」で一度だけ許可する。または自分で作成したファイルを使う |

### 3.4 Mac側の操作を最小限にする方法

**Macの標準機能だけでは、USBのシリアルをインターネットへ中継できない。** 何らかのスクリプトを動かす必要がある。そのうえで、選べる形は次のとおり。

| 形 | 毎回の操作 | 最初の準備 | 注意 |
| --- | --- | --- | --- |
| **A：ダブルクリックで起動する `.command` ファイル** | ファイルをダブルクリック（ターミナルが開く）。使い終わったら閉じる | ファイルに実行権限を付ける（`chmod +x`） | いちばん分かりやすく、止め方も明確 |
| B：Automatorで「アプリケーション」にする | アイコンをダブルクリック | Automatorで作成する | ターミナルが開かない。止め方を用意する必要がある |
| C：ログイン時に自動で待機する（ユーザーのLaunchAgent） | **何もしない**（USBにつなぐと自動で中継） | `~/Library/LaunchAgents` に設定ファイルを置く（管理者権限は不要【一般】） | 常に動くプログラムになるので、**職場の規則で許されるかを確認**。外し方を用意する |

- 「インストールしない」については、どの形も新しいアプリは入れず、macOS標準の `zsh`・`curl`・`stty`・`caffeinate` だけを使う
- 「毎回起動しない」を満たすのはCだけ。まずAで動作を確かめ、必要ならCにするのがよい

## 4. USBネットワーク方式（CDC-NCM）との比較

| 項目 | ② USBシリアル中継 | ① USBネットワーク（NCM） |
| --- | --- | --- |
| Mac側のソフト | 標準コマンドのスクリプト | 不要（macOSの標準機能【一般・要実機】） |
| Mac側の設定 | なし | **インターネット共有を有効にする（管理者権限）**。会社の管理（MDM）で禁止されていることが多い |
| 職場のネットワーク | Macの通常の通信として出ていく（プロキシにも対応できる） | MacがNAT・DHCPの役割をすることになる。**社内ネットワークの構成を変える操作で、管理者の許可が必要**。プロキシ必須の環境では通らない可能性 |
| Cardputer側の作業 | 小さめ（音声の入口と短いやり取り） | 大きい（NCMの記述子、受信・送信のつなぎ込み、ネットワークのインターフェース、経路の切り替え） |
| USBの設定 | 今のまま | USB-OTG（TinyUSB）に変更。約53KB増え、0x150000を超える（Launcherでの導入はできる見込み） |
| HTTPSの局 | 聴ける（Macが受信） | 聴けない（Cardputerが暗号化を処理する必要がある） |
| 難しさ | 低〜中 | 高 |

**再評価の結論：今、①を採用する利点は小さい。** 「Macにソフトなし」という利点はあるが、インターネット共有の管理者権限と職場の規則の壁が大きく、Cardputer側の作業も多い。職場の業務用ネットワークでは、②のほうが、ネットワークの構成を変えずに済む分、安全で現実的。

## 5. 職場での利用について（必ず守ること）

| 項目 | 方針 |
| --- | --- |
| インターネット共有 | **無断で有効にしない。** ①と、MacをWi-Fiの親機にする方法は、ネットワーク管理者の許可が必要 |
| 独自のWi-Fi（APモード） | Cardputerが自分でWi-Fiを出す方法も、職場では無線の出入口とみなされる可能性がある。許可なく使わない |
| Macの設定 | 既存のネットワーク設定は変えない。②のスクリプトは、ネットワークの設定に触れない |
| 常に動くプログラム | 方式②のC（LaunchAgent）は、職場の規則とセキュリティソフトの方針を確認してから |
| 機器の接続と音声の配信 | USB機器の接続、業務中の音声配信の利用、通信量について、職場の規則に従う |

## 6. 推奨する方式とその理由

**推奨：② USBシリアル中継（最初は形A、必要なら形C）**

1. **職場のネットワークの構成を変えない**（インターネット共有もWi-Fiの親機も使わない）
2. **Macに新しいソフトを入れない**（標準のコマンドだけで作るスクリプト）
3. **Cardputer側の変更が小さく**、デコーダー・選局・Location・地球儀などをそのまま使える
4. 社内プロキシに対応しやすい。**HTTPSの局も聴けるようになる**
5. Wi-Fiのある場所では、これまでどおりCardputerだけで動く

**満たせない希望**：「Macで毎回スクリプトを起動しない」は、形C（ログイン時に自動で待機）で満たせる。ただし、職場の規則によっては使えない。「Mac側に何も置かない」は、②では実現できない（①ならOSの機能だけで済むが、インターネット共有が必要）。

## 7. 実装する場合の段階的な開発計画（案）

| 段階 | 内容 | 判定 |
| --- | --- | --- |
| **U0** 事前確認（コード不要） | 職場のMacで、`curl` で放送局を受信できるか（プロキシ、ポート）。職場の規則の確認 | 受信できること |
| **U1** つながるかの試作 | Cardputer：シリアルからMP3を読んで再生するだけの試験版。Mac：1行のコマンド（`stty raw` と `curl` でポートへ書き込む）。**ポートを開いたときにリセットされないか**を最初に確かめる | 10分以上途切れずに再生できること。リセットされないこと |
| **U2** やり取りの形 | HELLO・TUNE・区切り・PINGを実装する。Mac側は `RadioDaysRelay.command`（形A）。選局、局の変更、記録との共存 | 速く選局しても、前の局が混ざらないこと |
| **U3** 切り替えと復帰 | USB／Wi-Fiの自動切り替え、抜き差しからの復帰、画面の「USB」の印 | 抜き差しでフリーズしないこと |
| **U4**（任意） | 形C（ログイン時に自動で待機）、HTTPSの局、曲名 | 職場の規則で許される場合のみ |

各段階は、これまでと同じく新しいフォルダで作る。Stage 3-3以前は変更しない。
