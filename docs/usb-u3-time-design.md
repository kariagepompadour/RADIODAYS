# U3（案）：USBだけのときも時計・太陽・月を出す（Macから時刻を受け取る）

- 作成日：2026-10-21
- 状態：**作者が承認（2026-10-21。名前はU3、時刻のもとの表示はなし）。実装は [usb-u3.md](usb-u3.md)**。実装では、`TIME` を頼み直すのは「書けなかったとき」か「10秒返事がないとき」だけにした（第3.2節の「PINGと一緒に数回」を具体化）
- 調べた版：U2a4（`firmware/RadioDays_U2a4/RadioDays_U2a4.ino`）、Macの中継U2a2（`RadioDaysRelay_U2a2.command`）
- これは、U2の設計で「U3」に回した項目（Macからの時刻）にあたる

---

## 1. 今の表示の条件と、時刻の取り方（U2a4）

| 項目 | 今の作り | 場所 |
| --- | --- | --- |
| 時刻の取り方 | **SNTPだけ**。Wi-Fiにつながったとき、`clockService()` が `configTzTime(JST, ntp.nict.jp, pool.ntp.org)` でSNTPを始める。同期すると、SNTPがシステムの時計を合わせ、`onTimeSync()` が `timeSynced = true` にする | `clockService()`、`onTimeSync()` |
| 表示の条件 | `clockValid()` ＝ `timeSynced` かつ時刻が2025年以降。**この起動でSNTPが同期するまで、時計は `--:--`、空の窓は何も描かない**（RTCに残った時刻は信用しない、という3-3までの決まり） | `clockValid()`、`drawClock()` |
| 時計の表示 | `localtime_r()` で、**日本時間（`JST-9`、固定）**。Locationに関係なく日本時間 | `drawClock()` |
| 太陽（昼と夜） | `solarAltitudeDeg(UTCの時刻, 緯度, 経度)`。**Locationの都市の緯度と経度と、UTCの時刻**から太陽の高さを計算し、−0.833°より上なら昼（太陽）、下なら夜（月）。1分に1回 | `updateSky()`、`skyPlace()` |
| 月 | `moonPhase01(UTCの時刻)`。月の満ち欠けは地球上どこでも同じなので、UTCの時刻だけ | `drawClock()` |
| USBだけのとき | Wi-Fiがない（または中継があるのでWi-Fiを止めている）ので、SNTPが始まらない → `timeSynced` はfalseのまま → 時計も太陽も月も出ない。**これが今回の現象の原因** | ― |

## 2. Wi-Fiで得た時刻が描画に届くまで

```text
SNTP（Wi-Fi） ──settimeofday──▶ システムの時計（UTCの秒）
                                  │
     onTimeSync() → timeSynced = true
                                  │  time(nullptr) ＝ UTCの秒
                                  ▼
drawClock()  ├─ localtime_r（TZ＝JST-9）→ 日付と「hh:mm」
             ├─ updateSky → solarAltitudeDeg(UTC, Locationの緯度経度) → 昼／夜
             └─ moonPhase01(UTC) → 月の形
```

- **描画は、システムの時計（UTCの秒）だけを使っている。** SNTP以外の方法でシステムの時計を合わせても、描画の処理はそのまま使える
- **日本時間への変換は、時計の文字だけ**。太陽と月はUTCと緯度経度で計算していて、時間帯（タイムゾーン）を使っていない。**国ごとの昼と夜は、もともとタイムゾーンと無関係に正しく出る**
- 注意（調べてわかったこと）：時間帯の設定（`setenv("TZ", "JST-9")`）は、**SNTPを始めるときにしか行っていない**。SNTPなしで時計を合わせると、時計の文字がUTC（日本時間より9時間遅れ）になってしまう

## 3. Macから時刻を送れるか

**送れる。** ただし、MP3のデータの途中には文字の行を入れられない（U2aの設計：返事の行は、Cardputerが待っている間だけ）。

### 3.1 やり取り（案）：後から加えても、どちらの古い版とも組み合わせられる形

| 方向 | 行 | 内容 |
| --- | --- | --- |
| Cardputer→Mac | `@RD TIME <id>` | 時刻をください（新しいid） |
| Mac→Cardputer | `\nRDTIME <id> <UTCの秒>\n` | 例：`RDTIME 3f2a91c4 1792569600` |

| 組み合わせ | 動き |
| --- | --- |
| 新しいCardputer＋新しい中継 | 時刻が届く |
| 新しいCardputer＋**中継U2a2** | U2a2は知らない行を無視する（ターミナルに「Ignored」と1行出る）。時刻は届かず、今と同じく `--:--`。**再生には影響しない** |
| **U2a4以前**＋新しい中継 | Cardputerが頼まないので、中継は何も送らない。**今と同じ** |

`RDHOST` の行に時刻を足す方法は採らない（U2a4以前は `RDHOST <id>` と完全一致で探すので、つながらなくなる）。

### 3.2 いつ頼むか

| 項目 | 案 |
| --- | --- |
| 頼む時 | 中継が見つかったとき（L0→L1）に1回。届かなければ、L1にいる間、PINGと一緒に数回まで |
| 受け取れる状態 | L0・L1・L2（MP3を受け取っていない間）。中継が見つかるとすぐ選局（TUNE）が続くので、返事がL2で届くことがある。そのためL2でも受け取る |
| 受け取れない状態 | L3（受信中）。この間は文字の行を探さない（今のまま） |
| 取り違えの防止 | `RDTIME` にも頼んだときのidを付ける（U2aと同じ考え方）。古いMP3データの中の偽の行と取り違えない |
| 数字の読み取り | 手書き（`sscanf` は使わない。U2aの容量の調査） |

### 3.3 タイムゾーンの扱い（Macのローカル時刻と混同しない）

| 項目 | 案 |
| --- | --- |
| Macが送るもの | **UTCの秒（Unix時刻）だけ**。Perlの `time` は、Macの時間帯の設定に関係なくUTCの秒を返す。年月日や「hh:mm」の文字、Macのローカル時刻、Macの時間帯は送らない |
| Cardputerでの使い方 | 受け取ったUTCの秒で、システムの時計を合わせる（SNTPと同じ） |
| 時計の表示 | 今までどおり**日本時間（JST-9、固定）**。そのために、時間帯の設定（`setenv("TZ", "JST-9")`）を、SNTPのときだけでなく**起動時に1回**行う |
| 太陽と月 | 今までどおり、UTCとLocationの緯度経度だけで計算する。Macの場所や時間帯は使わない |
| 例 | Macを海外の時間帯にしていても、送るのはUTCの秒なので、Cardputerの時計は日本時間、ロンドンのLocationの昼夜はロンドンの太陽の高さで決まる |

### 3.4 時刻のもとの優先

| 場合 | 案 |
| --- | --- |
| SNTP（Wi-Fi）で同期済み | Macの時刻は使わない（SNTPを優先） |
| Macの時刻を使った後で、SNTPが同期した | SNTPが上書きする（どちらもUTCなので、そのまま正しくなる） |
| Macの時刻がおかしい | 2025年より前、または2100年より後の値は使わない。Macの時計がずれていれば、Cardputerも同じだけずれる（Macは普段、自動で時刻を合わせている【一般】） |

## 4. USBが切れても時計は進むか

**進む。**

- ESP32-S3のシステムの時計は、一度合わせると、本体の中のタイマー（水晶発振）で進み続ける。ネットワークやUSBの接続は必要ない。今のWi-Fiの時計も、SNTPの同期の間はこの仕組みで進んでいる
- ずれは、1日に数秒以下の見込み【推測：水晶の精度による。実測していない】。中継がつながり直すたびに、もう一度時刻を受け取る（3.2節）
- **再起動すると消える**（本体には時計のチップを使っていない：`cfg.internal_rtc = false`。3-3までの「RTCの時刻は信用しない」という決まりもある）。再起動の後は、中継がつながると、また時刻を受け取る
- USBが抜けている間も、時計・太陽・月は表示され続ける。抜けている間の時刻は、最後に受け取った時刻から本体のタイマーで進めたもの

## 5. 最小変更案

### 5.1 Cardputer（新しい版）

| 変更 | 内容 | 影響 |
| --- | --- | --- |
| `radiodays_link.h` | L0→L1で `@RD TIME <id>` を1回送る（届かなければPINGのときに数回まで）。L0〜L2の行の照合に `RDTIME <id> <数字>` を加え、届いた秒を原子的な変数に置く（`timeFromRelay()` で読む）。L3は何も変えない | MP3の受け取り、クレジット、選局、取り違えの防止は今のまま |
| スケッチ：時計 | `clockService()` に数行：SNTPで同期していなければ、中継の時刻で `settimeofday()` し、`timeSynced = true`。時刻のもとを記録（`[CLOCK] time from the Mac relay`） | 描画の処理（`drawClock`・太陽・月）は変えない |
| スケッチ：時間帯 | `setenv("TZ", "JST-9")`・`tzset()` を `setup()` で1回（SNTPのときの設定はそのまま） | 時計の文字が常に日本時間になる |
| UFO、選局、音量、Wi-Fi、USB専用起動 | 変えない | ― |
| 大きさ | 約+0.5〜1KB【推測】。残りは約13KB | ― |

（任意）時刻のもとの表示（例：時計の横に小さく「M」）。**今回の最小案には入れない**。

### 5.2 Mac（新しい中継。U2a2は残す）

- `@RD TIME <id>` を受け取ったら、すぐに `\nRDTIME <id> <time>\n` を返す（`time` はPerlのUTCの秒）
- Cardputerは、MP3を受け取っている間（L3）には頼まない。そのため、返事の行がMP3のデータの途中に入ることはない（U2aの「返事は待っている間だけ」という決まりを守る）。念のため、中継は `RDSYNC` を送った後（MP3を送っている間）に `@RD TIME` が届いても答えない。局につないでいる途中（`RDSYNC` の前）なら答える
- それ以外はU2a2と同じ。U2a4以前のCardputerとも組み合わせられる（第3.1節）

### 5.3 名前（案）

- **U3**（ファームウェア `RadioDays_U3`、中継 `RadioDaysRelay_U3.command`）。U2の設計で「Macからの時刻はU3」と決めていたため
- Wi-FiとUSBの自動切り替え（U2b）は、今回も含めない

## 6. 試験の案

| 種類 | 内容 |
| --- | --- |
| シミュレーション（sim2を広げる） | 中継が見つかると時刻が届く／TUNEの直後（L2）に届いても受け取る／idの違う `RDTIME`、古いMP3データの中の偽の `RDTIME` を無視する／中継U2a2との組み合わせ（時刻は届かず、再生は今までどおり）／U2a2の41項目と確認用 |
| ホスト試験 | 時刻を受け取った後、時計の文字が日本時間になること（Macの時間帯を変えても同じ）／ロンドン・ニューヨーク・東京の昼夜が、UTCと緯度経度で決まること／SNTPで同期済みならMacの時刻を使わないこと／2025年より前の値を使わないこと |
| 実機 | 職場（USBだけ・`U`）で、中継が見つかると時計・太陽または月が出る／USBを抜いても時計が進む／Wi-Fiで今までどおり（SNTP）／UFOとUSBの再生がU2a4と同じ |

## 7. まとめ

1. 太陽・月が出ないのは、時刻をSNTPからしか受け取らず、USBだけのときはSNTPが動かないため
2. 描画はシステムの時計（UTC）だけを使うので、Macから時刻を受け取ってシステムの時計を合わせれば、描画の処理を変えずに表示できる
3. MacはUTCの秒だけを送る。時計の表示は日本時間（固定）、太陽はUTCとLocationの緯度経度。Macのローカル時刻は使わない
4. 一度合わせれば、USBが切れても本体のタイマーで時計は進む（再起動で消え、つながり直すと再び受け取る）
5. やり取りは、`@RD TIME`／`RDTIME` を足すだけで、古い版とも組み合わせられる。MP3の受け取りの部分（L3）、UFO、Wi-Fiの動きは変えない
