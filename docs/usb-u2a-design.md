### 第1版からの主な変更

| 変更 | 理由 |
| --- | --- |
| すべての要求に、**推測できない番号（id）**を付ける。返事は同じidを返す | 古い返事・古いデータの中の文字列を、今の返事と取り違えないため |
| Macは、**局の応答ヘッダーを確かめてから** `RDSYNC` を送る。だめなら `RDNAK` | 接続の失敗、許可していないリダイレクトも、MP3を送り始める前に伝えられる |
| 返事の行の前に改行を1つ付ける（`\nRDSYNC …\n`） | 古いMP3データの直後でも、返事が必ず行の先頭から始まるため |
| TUNEの送り直しをやめ、選局の待ち時間を12秒の1種類にする | Macは10秒以内に必ず返事をする。送り直しは状態を複雑にするだけだった |
| シリアルの受信を読むタスクを、状態ごとに1つに決める | 状態が変わる瞬間に、別のタスクが古いデータを読むのを防ぐ |
| Macは `curl` にリダイレクトを任せず、自分で1つずつ確かめる | リダイレクト先にも、ホストとポートの制限をかけるため |

## 1. 守ること（古い局と新しい局のデータを混ぜない）

| 原則 | 内容 |
| --- | --- |
| idで区別する | 要求のたびに新しいidを使う。idは32ビットの数で、起動時に乱数から始め、1ずつ増やす。行の中では16進数8桁（小文字）で書く |
| 区切りまでは捨てる | Cardputerは、TUNEを送ってから `RDSYNC <id>` を見つけるまで、届いたバイトをすべて捨てる |
| 順番が保証されている | USBシリアルは送った順に届く。Macは1つの流れで動き、古い局のデータを書き終えて `curl` を止めてから、区切りを書く。**区切りの後には新しい局のデータしかない** |
| 新しい局のデータはクレジットの後だけ | Macは、`RDSYNC <id>` を書いた後に届いた `@RD MORE <id> …` の分しか送らない。Cardputerは区切りを見つける前にMOREを出さない |
| 読むタスクは1つ | 受信キューを読むのは、L3では再生用タスクだけ、それ以外ではリンクの管理だけ（第3.3節） |
| バッファーは作り直す | 32KBのストリーム用バッファーの入れ物は、局ごとに作り直す。作るのは区切りを見つけた後だけ |

## 2. やり取り（U2a）

### 2.1 Cardputer→Mac（文字の行だけ。バイナリは送らない）

| 行 | 意味 | Macの返事 |
| --- | --- | --- |
| `@RD HELLO U2 <id>` | 中継を探している（L0で2秒ごと） | `RDHOST <id>` |
| `@RD PING <id>` | 中継が動いているかの確認（L1で2秒ごと） | `RDHOST <id>` |
| `@RD TUNE <id> <URL>` | この局を受信して | 10秒以内に `RDSYNC <id>` か `RDNAK <id> <理由>` |
| `@RD STOP <id>` | 受信を止めて | なし（次のPINGで確かめる） |
| `@RD MORE <id> <n>` | 局idのデータを、あとnバイト送って（idはTUNEのid） | なし（データで応える） |
| `[`で始まる行など | Cardputerの記録 | 画面に表示するだけ |

- 各行は `Serial.printf` 1回で書く。Arduinoコアの `HWCDC::write` は、1回の書き込みの間、送信用のロックを持つ【確認：`HWCDC.cpp` 540〜621行】。そのため、コア0の記録とコア1の要求が、1行の途中で混ざることはない
- ただし、Macが読まない状態が続くと、書き込みが途中で打ち切られることがある。Macは、形の正しくない行を無視する（第6節）

### 2.2 Mac→Cardputer

| 行 | 意味 |
| --- | --- |
| `\nRDHOST <id>\n` | 中継が動いている |
| `\nRDSYNC <id>\n` | 局の応答を確かめた。ここから先は局idのデータ（ただし、MOREの分だけ） |
| `\nRDNAK <id> <理由>\n` | その局は受信できない。理由：`URL`（形が正しくない）、`HOST`（許可していないホスト）、`PORT`（許可していないポート）、`REDIR`（リダイレクト先が許可外、またはHTTPS、または多すぎる）、`HTTP`（200以外の応答）、`CONN`（つながらない、または10秒以内に応答がない） |
| MP3のデータ | `RDSYNC` の後、クレジットの分だけ |

- **返事の行は、Cardputerが要求を出して待っている間（L0・L1・L2）にだけ送る。** L3（受信中）のCardputerは要求を出さない（MOREと記録だけ）ので、MP3の途中に文字の行が入ることはない
- 行の前に改行を付けるのは、直前に捨てられる古いMP3データがあっても、返事を行の先頭から読めるようにするため

### 2.3 Cardputerが返事を見つける方法（分割受信への対策）

- リンクの管理は、受け取ったバイトを1つずつ、32バイトの「行の入れ物」に入れる。改行で入れ物を空にする
- 改行が来たとき、入れ物の中身が**今待っている返事とちょうど同じ**（例：`RDSYNC 3f2a91c0`）なら、見つけたとする
- 32バイトを超えた行（MP3データのほとんど）は、次の改行まで「無効」として捨てる
- 入れ物は、読み出しの回をまたいで残る。**`RDSYNC` が何回に分かれて届いても、正しく見つけられる**
- 待っているidと違う返事（古いidの `RDSYNC`・`RDNAK`・`RDHOST`）は、捨てるデータとして扱う
- 古いMP3データの中に、今待っている返事と同じ17〜18バイトの並びが偶然あり、しかも前後が改行である確率は、実用上0【推測：idは送る直前に決まり、古いデータとは関係がない】

## 3. 状態遷移

### 3.1 Cardputer（リンクの管理。画面のタスク、コア1）

```text
                        RDHOST <id>
  [L0 中継なし] ─────────────────────────▶ [L1 中継あり・待機]
   ▲  HELLO 2秒ごと                          │ ▲   PING 2秒ごと
   │  バイトはすべて捨てる                     │ │   バイトはすべて捨てる
   │                                         │ │
   │ 6秒RDHOSTなし（L1）                  TUNE │ │ RDNAK／STOP
   │ 12秒返事なし（L2）                       ▼ │
   │ USBが抜けた（すべて）              [L2 選局中(id)]
   │                                    バイトを捨てながら返事を探す
   │                                         │ RDSYNC <id>
   │                                         ▼
   └──────────────────────────────── [L3 受信中(id)] ── 再生用タスクが読む
                          5秒データなし → STOP → L1
                          選局・停止の要求 → STOP（またはTUNE）→ L1／L2
```

| 状態 | 受信キューを読むのは | すること | 出ていく条件 |
| --- | --- | --- | --- |
| **L0 中継なし** | リンクの管理 | USBのホストがいれば、2秒ごとにHELLO（毎回新しいid）。行の入れ物で `RDHOST <最後に送ったid>` を探す | 見つけた → L1 |
| **L1 待機** | リンクの管理 | 2秒ごとにPING。すべて捨てる（STOPの後に残る古いデータを含む） | 選局の要求 → L2。6秒間、RDHOSTがない → L0 |
| **L2 選局中(id)** | リンクの管理 | TUNEを送る。捨てながら `RDSYNC <id>`・`RDNAK <id> …` を探す。**MOREは出さない** | RDSYNC → L3。RDNAK → L1（再生用タスクに「受信不可」と知らせる）。新しい選局の要求 → 新しいidでL2。停止の要求 → STOPを送ってL1。12秒返事なし → L0 |
| **L3 受信中(id)** | 再生用タスク | クレジットを出す（第4節）。リンクの管理は受信キューを読まない | 次の選局・停止の要求 → 読み手を止めて（第3.3節）、STOPまたはTUNEを送り、L1またはL2。5秒データなし（第6節）→ 同じくL1 |
| （すべての状態） | ― | 1秒ごとに `Serial.isConnected()` を確かめる | falseならL0（再生用タスクに知らせる） |

### 3.2 Mac（`RadioDaysRelay_U2.command`、1つの流れで動く）

Macの「局」の状態：**なし** →（TUNE）→ **接続中(id)** →（応答を確かめた）→ **送信中(id)**

| 受け取った行 | すること |
| --- | --- |
| `@RD HELLO U2 <id>` | **すべてやり直す**：`curl` を止め、クレジットを0、局をなしにして、`RDHOST <id>` を返す |
| `@RD PING <id>` | 局が接続中か送信中なら止める（Cardputerは待機中なので、局は要らない）。`RDHOST <id>` を返す |
| `@RD TUNE <id> <URL>` | ① 今の `curl` を止める（これで古い局のデータはもう書かない）。クレジットを0、局をなしにする<br>② URLの形・ホスト・ポートを確かめる（第7節）。だめなら `RDNAK <id> <理由>` を返して終わり<br>③ `curl` を始め、局を「接続中(id)」にする<br>④ 応答ヘッダーを読む。リダイレクトなら行き先を②と同じ基準で確かめ、新しい `curl` にする（3回まで）<br>⑤ `200` なら `RDSYNC <id>` を書き、局を「送信中(id)」にする。だめなら `RDNAK <id> <理由>`<br>※ ③〜⑤の間も、Cardputerからの行は受け付ける。新しいTUNE・STOP・HELLO・PINGが来たら、今の接続をすぐやめてそちらに従う |
| `@RD STOP <id>` | `curl` を止め、クレジットを0、局をなしにする |
| `@RD MORE <id> <n>` | 局が「送信中(id)」のときだけ、クレジットにnを足す。それ以外（古いid、接続中、局なし）は無視する |
| 形の正しくない行 | 無視する（記録として表示するだけ）。1行は1,024バイトまで。超えた分は捨てる |
| （送信中に `curl` が終わった） | 2秒後に同じURLへつなぎ直す。④と同じ確認をし、ヘッダーは送らずに本文だけを続ける（区切りは送らない。MP3デコーダーが自分で同期し直す）。だめなら2秒ごとにやり直す |
| （ポートが消えた・書けない） | `curl` を止め、局をなしにし、ポートが現れるまで2秒ごとに探す（スクリプトは終わらない） |
| （接続中に10秒たった） | `curl` を止めて `RDNAK <id> CONN` |

- Macは、`RDSYNC <id>` より前に、その局のMP3データを1バイトも書かない。ヘッダーと一緒に読んだ本文の先頭は、Mac側で取っておき、クレジットが来てから送る
- 古い局の `curl` は①で止めるので、②以降に古い局のデータが書かれることはない

### 3.3 読み手の受け渡し（L3から出るとき）

L3では、再生用タスク（コア0）が受信キューを読む。L3から出るとき、リンクの管理（コア1）が読み始める前に、再生用タスクが読み終わっていることを確かめる。

| 再生用タスク（シリアルの入口 `take()`） | リンクの管理（L3から出るとき） |
| --- | --- |
| ① `readerBusy = 1` | ① `linkState` をL3以外にする |
| ② `linkState` がL3で、`linkId` が自分の待つidでなければ、`readerBusy = 0` にして0バイトを返す | ② `readerBusy` が0になるまで待つ（最大で1回の読み出しの間） |
| ③ `Serial.read()` | ③ ここから受信キューを読む（捨てる） |
| ④ `readerBusy = 0` | |

- 変数はすべて `std::atomic`（順序の保証つき）。①と②の順番があるので、両方が同時に読むことはない
- 再生用タスクが③で読んだバイトは、STOPやTUNEを送る前のもの、つまり**今の局のデータ**。新しいTUNEは、②の後でしか送らない

## 4. クレジットの管理

### 4.1 基本（U1と同じ。U1で実機検証済み）

| 項目 | 内容 |
| --- | --- |
| 受信キュー | 16KB（`Serial.setRxBufferSize(16384)` を起動時に1回だけ設定） |
| クレジットの単位 | 2KB。余裕として1KBは空けておく |
| 局ごとに数える | L3に入ったとき、`granted`（許可した量）と `taken`（読み出した量）を0にする |
| 出す条件 | キューにある量＋届いていない量（`granted −（taken＋キューの量）`）＋2KB＋1KB が16KB以下のとき |
| あふれない理由 | 「許可した量−届いた量」が、いつもキューの空き以下になるように許可するため |

### 4.2 場面ごとの扱い

| 場面 | 古い局の、Macが書いたがまだ届いていないデータ | Macに残っている、使われていないクレジット | Cardputerの受信キューにあるデータ | 新しい局のクレジット |
| --- | --- | --- | --- | --- |
| **選局**（L3→L2） | 区切りより前に届くので、L2で捨てる | TUNEの①で0にする | L2で捨てる（読み手の受け渡しの後） | L3に入るときに0から数える。MacはRDSYNCを書いた後のMORE（同じid）だけ数える |
| **連続選局**（L2の間に次の選局） | Cardputerは前のidにMOREを出していないので、前の局のデータは送られていない | 前のidは0のまま | 古い局の残りがあれば捨てる | 最後のidのRDSYNCの後から。前のidのRDSYNC・RDNAKは無視する |
| **停止**（MANUALのノイズ、Locationの変更） | L1で捨てる | STOPで0にする | L1で捨てる | ― |
| **選局のタイムアウト**（L2で12秒） | L0で捨てる | 次のHELLOで0にする | L0で捨てる | 次のTUNEから |
| **受信中のタイムアウト**（L3で5秒データなし） | STOPの後、L1で捨てる | STOPで0にする | L1で捨てる | 再生用タスクが開き直すときの、新しいTUNEから |
| **USBが抜けた・Macのスクリプトの再起動** | L0で捨てる | Macは局をなしにする（再起動ならもともと0） | L0で捨てる | 次のHELLO（Macはすべてやり直す）→PING→TUNEから。再起動したMacは、知らないidのMOREを無視する |
| **MOREの行が途中で切れた** | ― | Macは形の正しくない行を無視するので、その2KBは許可されない | ― | Cardputerは「届いていない量」が2KB多いと思うので、許可が2KB控えめになる（あふれる方向には間違えない）。次にL3に入るとき0に戻る |

**RDSYNCの後に古いデータが混ざらない理由（まとめ）**

1. Macは、TUNEを受け取ると、まず古い `curl` を止める。その後、古い局のデータは書かない
2. Macは、`RDSYNC <id>` を書いた後、同じidのMOREの分だけ、新しい局のデータを書く
3. USBシリアルは順番を変えない。そのため、Cardputerに届く順番は「古いデータ → `RDSYNC <id>` → 新しいデータ」
4. Cardputerは、`RDSYNC <id>` を見つけるまですべて捨てる。見つけた時点で、まだMOREを出していないので、その後ろに新しいデータはまだない。キューは空で、L3の数え方は0から正しく始まる
5. 読み手の受け渡し（第3.3節）があるので、古いデータを再生用タスクが読むこともない

## 5. 選局のときの順序（再生用タスク、コア0）

USBが確立しているとき、局を開く処理（今の `new AudioFileSourceICYStream(url)` の部分）を、次の順に置き換える。

| 順番 | 処理 | ねらい |
| --- | --- | --- |
| 1 | `stopStream()`：メーターの印を下ろし、デコーダーを止めて削除し、バッファーの入れ物を削除し、スピーカーに残った音を出し切る | 古い局の音と、古いデータの入れ物をなくす |
| 2 | リンクの管理（コア1）に「局を選んで」と頼む（原子的な変数で渡す）。リンクの管理が、L3なら読み手の受け渡し（第3.3節）をし、新しいidを決めてTUNEを送る | シリアルへの要求の書き込みは、コア1だけが行う |
| 3 | 頼んだ選局のidを受け取り、シリアルの入口が待つidにする | 入口が古いidのデータを返さない |
| 4 | リンクがL3（同じid）になるのを待つ。新しい選局の要求、ラジオの停止、リンクの切断、RDNAKがあれば、すぐにやめる | 区切りの後だけを使う |
| 5 | 新しいバッファーの入れ物を作る（32KBの領域は使い回す）。中身は空から始まる | 古いデータが残らない |
| 6 | 3/4（約1.5秒分）まで貯める（今と同じ） | 再生の安定 |
| 7 | 新しいMP3デコーダーを作って再生を始める | ― |

MANUALで局から外れたとき（ノイズ）は、ノイズに入る前に、リンクの管理に停止を頼む（STOPを送る）。ノイズは今までどおりCardputerの中で作る。

## 6. タイムアウトと失敗のときの処理

| 場面 | 時間 | 処理 |
| --- | --- | --- |
| HELLOへの返事 | 2秒ごとに送り続ける | 返事が来るまでL0 |
| PINGへの返事 | 6秒 | 返事がなければ、中継はないとみなす（L0） |
| TUNEへの返事 | 12秒（Macは10秒以内に必ず返す） | 中継が止まったとみなす（L0）。再生用タスクは「NO SIGNAL」として、中継が戻ってから選局し直す |
| RDNAK | すぐ | 「NO SIGNAL」と表示する。理由はシリアルの記録に出す。ダイヤルで別の局を選ぶまで、その局は再試行しない（`CONN`・`HTTP` の場合は、今の局と同じく10秒後にやり直す） |
| 受信中の停止 | 5秒 | クレジットを出しているのにデータが来ない。STOPを送ってL1。再生用タスクは、今の「ストリームが終わったら開き直す」処理で、新しいidでTUNEする |
| 再生が止まってキューがいっぱい | ― | クレジットを出さないだけで、タイムアウトにはしない（「届いていない量」が0なので、停止とはみなさない） |
| USBが抜けた | 1秒 | `Serial.isConnected()` がfalseならL0。再生用タスクは止まる（Wi-Fiへの切り替えはU2b） |
| 選局の途中でUSBが抜けた | 1秒 | L2からL0。再生用タスクは第5節の4でやめる。つなぎ直した後は、HELLO→PING→TUNE（新しいid）で始め直す |
| Macのスクリプトが止まった | 5〜12秒 | L3なら「データが来ない」、L1なら「返事がない」、L2なら「TUNEへの返事がない」でL0に戻る |
| Macで、局が送信中に切れた | 2秒ごと | Macがつなぎ直す。5秒以上かかれば、Cardputerが先に「データが来ない」でL1に戻り、新しいTUNEで始め直す（Macはつなぎ直しをやめる） |

## 7. Macの許可ホストとポート

| 項目 | 内容 |
| --- | --- |
| 一覧 | **ホストとポートの組**。例：`stream.radioparadise.com:80`、`ottava2.out.airtime.pro:8000`。スクリプトの中に `stations.h` の全局分を持つ。スクリプトと同じフォルダに `allowed_hosts.txt` があれば、その一覧だけを使う |
| 判定 | ホスト名は完全一致（大文字・小文字は区別しない）。ポートも完全一致。URLにポートがなければ80とみなす |
| URLの形 | `http://ホスト[:ポート]/パス` だけを受け付ける。ホストは英数字・`-`・`.`だけ。ポートは1〜65535。パスは使える文字だけ。全体で300文字以内 |
| 受け付けないURL | `https://` などほかの方式（決定3）、`ユーザー名@` を含むもの、`#` を含むもの、IPアドレスで書いたホスト、`-` で始まるもの |
| リダイレクト | `curl` に任せない（`-L` を使わない）。Macが応答ヘッダーの `Location` を読み、**最初のURLと同じ基準**（形・ホスト・ポート・httpだけ）で確かめてから、新しい `curl` でつなぐ。3回まで。相対パスの `Location` は、今のURLのホストとポートを使う |
| `curl` の設定 | `--proto '=http'`（HTTP以外を使わない）、`--max-redirs 0`、`-i`（応答ヘッダーを受け取る）、`--http0.9`（第7.1節）、`--connect-timeout 8`、`-A 'RADIODAYS-relay/U2'`。URLは1つの引数として渡し、シェルを通さない |
| 拒否したとき | `RDNAK <id> <理由>` を返し、Macの画面にURLと理由を表示する |
| 職場での注意 | 社内プロキシ（`http_proxy`）を使う場合、許可の判定はURLのホストとポートで行い、プロキシのアドレスは判定しない |

### 7.1 調べてわかったこと（2026-10-21、作業用のMacで確認）

| 項目 | 結果 |
| --- | --- |
| `ICY 200 OK` で答える古い型のサーバー | このMacの `curl` 8.7.1は、そのままでは「HTTP/0.9は許可されていない」として受信をやめる。`--http0.9` を付けると、応答をそのまま渡すので、Macのスクリプトが状態の行（`HTTP/1.x 200`・`ICY 200`）とヘッダーを自分で読む【確認：ローカルの試験用サーバー】 |
| 今の27局の応答（`--http0.9 --max-redirs 0 --proto '=http'`） | 24局が `HTTP/1.0 200` か `HTTP/1.1 200`（SomaFMの2局は下の行）。`ICY 200` で答える局はなかった。**SRG SSRの1局（`stream.srg-ssr.ch`）は、同じホストの別のパスへ302でリダイレクトする**（httpのまま、ポート80）。許可の基準を満たす |
| SomaFMの2局 | 利用者を表す名前（`-A`）を付けないと、空の応答になった。付けると `200`。U1のスクリプトと同じく、必ず付ける |

## 8. 容量の見積もりと削減できるところ

### 8.1 実測（一時フォルダでの試作ビルド。リポジトリには入れていない）

| 試作 | 増加 | 0x150000までの残り |
| --- | --- | --- |
| （基準）Stage 3-3 | ― | 21,072 B |
| 受信キューを16KBにするだけ | +16 B | 21,056 B |
| リンク管理の中心（数字の読み取りは手書き） | **+1,328 B** | 19,744 B |
| 同じ処理で、数字の読み取りに `sscanf` を使った場合 | **+17,504 B** | 3,568 B |

**`sscanf` を使うと、書式つきの読み取りの仕組み一式（約16KB）がリンクされる。** 数字の読み取り（16進数のid、10進数のバイト数）は手書きにする。同じ理由で、まだ使っていない標準関数の書式つき入出力・`std::string`・正規表現は使わない。`Serial.printf` はすでに使っているので、追加の費用はない。

### 8.2 U2a全体の見積もり（第2版）

| 追加 | 見込み |
| --- | --- |

| UFOの位置の変更（第11節） | ほぼ0 |
| **合計** | **約3〜4KB**。残りは約17〜18KB【推測】 |

Macの許可ホストとリダイレクトの確認は、Mac側のスクリプトなので、Cardputerの容量には関係しない。

## 9. 事前のテスト（シミュレーション）

U1と同じ仮想シリアルポート（pty）での試験を広げる。Cardputer側はスケッチから取り出したリンク管理（偽のUSB割り込みは、Arduinoのドライバーと同じく、キューがいっぱいなら捨てる）、Mac側は実際のスクリプトU2を使う。放送局の代わりに、ローカルの試験用サーバーを使う。

### 9.1 正常系

| テスト | 合格の条件 |
| --- | --- |
| 局ごとに違う模様のデータを流し、選局を10回くり返す | 区切りの後に読んだバイトが、**すべてそのidの局のもの**。捨てられたバイト（あふれ）0 |
| 128kbps相当で再生、4秒の一時停止、4倍の速さで読む | U1と同じく、あふれ0、データが元と一致 |
| `ICY 200 OK` で答えるサーバー | ヘッダーを取り除いた本文だけが届く |
| 同じホストへのリダイレクト（SRG SSRと同じ形） | リダイレクト先の本文が届く |

### 9.2 異常系：データの混入と境界

| テスト | 合格の条件 |
| --- | --- |
| 区切りの分割受信：Macからのバイトを、1バイトずつ・ランダムな大きさで届ける | RDSYNCを毎回正しく見つける。混ざりなし |
| 古い局のデータの中に、`\nRDSYNC <古いid>\n`・`\nRDSYNC <今のid以外>\n`・`RDSYNC` で始まる壊れた行を入れておく | 取り違えない |
| 区切りの前のTUNE：TUNE(a)の直後、返事の前にTUNE(b) | bの局だけが再生される。aのRDSYNCは無視される。aのデータは届かない |
| 送信中にTUNE（Macがクレジットの分を書いている途中） | 古いデータはすべて捨てられ、混ざりなし |
| STOP→TUNE、TUNE→STOP→TUNE | 最後のidの局だけ |
| 古いidのMOREを、TUNEの後にわざと送る | Macが無視し、新しい局のデータが許可より多く届かない（あふれ0） |
| MOREの行を途中で切る | Macが無視する。あふれ0。再生は続く |
| 再生用タスクの読み出しの途中で、L3から出す（読み手の受け渡し） | 古いデータを再生用タスクが読まない。両方が同時に読まない |

### 9.3 異常系：切断とタイムアウト

| テスト | 合格の条件 |
| --- | --- |
| 選局の途中（L2）でポートを閉じる、またはUSBの切断を模擬する | CardputerはL0、Macは局をなしにして、ポートを探し続ける。つなぎ直すと、HELLO→PING→TUNEで再生が戻る |
| 受信中（L3）にMacのスクリプトを止めて、もう一度起動する | Cardputerは5秒でL1→L0。再起動したMacと、新しいidでつながる |
| 試験用サーバーが応答しない（接続したまま何も送らない） | Macが10秒で `RDNAK <id> CONN`。Cardputerは「NO SIGNAL」 |
| Macが返事をしない（スクリプトの代わりに、何も返さない相手） | Cardputerが12秒でL0 |
| 試験用サーバーが送信中に切れる | Macが2秒後につなぎ直す。本文だけが続く |

### 9.4 異常系：許可ホストとポート

| テスト | 合格の条件 |
| --- | --- |
| 許可したホスト・許可していないポート | `RDNAK <id> PORT`、`curl` を始めない |
| 許可していないホスト | `RDNAK <id> HOST` |
| 許可していないホストへのリダイレクト／許可したホストの別のポートへのリダイレクト | `RDNAK <id> REDIR`。リダイレクト先へはつながない |
| HTTPSへのリダイレクト | `RDNAK <id> REDIR` |
| 4回以上のリダイレクト、自分自身へのリダイレクト | `RDNAK <id> REDIR` |
| `ユーザー名@`・`#`・IPアドレス・`-` で始まる値・300文字を超えるURL・使えない文字を含むURL | `RDNAK <id> URL`、`curl` を始めない |
| `allowed_hosts.txt` を置いた場合 | その一覧だけが使われる |
| （確認用）クレジットなしで一気に送る | あふれを検出して不合格になる（テストの確かめ） |
