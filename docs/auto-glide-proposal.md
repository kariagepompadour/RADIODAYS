# AUTOの選局アニメーション（スケールが次の局まで流れる）：調査と設計提案

- 作成日：2026-10-22
- 状態：**作者が承認し、U8で実装**（[usb-u8.md](usb-u8.md)）。秒速100ピクセル、到着したらすぐ受信、移動中は TUNING...、先の局は最大3局

## 1. 今のAUTO選局の仕組み（U6・U7）

| 段階 | 処理 |
| --- | --- |
| ノブを回す | `tuneBy()`：`dialFreq` を**すぐ**次（前）の局の位置にする（端で一周）。`tunePending` を立てる |
| 画面 | 次の `drawRadio()`（100ミリ秒ごと）で、ダイヤルが新しい位置へ一度に描き直される（跳ぶ） |
| 音 | `tuneService()`：ノブが350ミリ秒止まったら、局の番号を復号のタスクに送る（`sendTarget()`）。それまで**前の局が鳴り続ける**（状態は「TUNING...」） |
| 復号のタスク（コア0） | 新しい要求を受けると、今の局を閉じ（`stopStream()`。USBなら中継へ `STOP`）、新しい局を開く（Wi-FiはHTTP、USBは `TUNE`→`RDSYNC`） |

MANUALでは、局の間に入ると `sendTarget(REQ_NOISE)` で**すぐ雑音**にし（局の再生と中継は止まる）、局に合って350ミリ秒止まると局を開く。

## 2. スケールを一定の速さで動かす方法（案）

- 「目標の局」と「今表示している位置」を分ける。AUTOでノブを回すと目標の局だけを決め、`dialFreq` は**1段（2ピクセル）ずつ**目標へ進める
- 進め方は**時間から計算**する（`開始位置 ＋ 速さ × 経過時間`）。`loop()` の遅れがあっても、速さは一定のまま（描くこまが1つ飛ぶだけ）
- 描くのは、動いている間だけ、ダイヤルの部分だけを20ミリ秒ごと（`drawDial()`。U6の差分の描き方そのもの）。止まっている間は今までどおり100ミリ秒ごとの `drawRadio()`
- 継ぎ目（最後の局→最初の局）も、1段ずつ一周の中を進むだけなので途切れない（U6の試験で、どの1段の移動も「前の絵を2ピクセルずらした絵」になることを確認済み）
- 新しいタスクや待ちは使わない（`loop()` の中で時刻を見て進めるだけ）。画面外のキャンバスも使わない

## 3. 移動中の雑音

- **MANUALの雑音の処理をそのまま使える**：動き始めに `sendTarget(REQ_NOISE)` を1回送るだけで、復号のタスクが今の局を閉じ（USBは中継へ `STOP`）、雑音を作り始める。これはMANUALで局の間に入るときと同じ道
- 着いたら局の番号を送る（`sendTarget(局)`）。復号のタスクは雑音を止め、新しい局を開く。MANUALで局に合わせたときと同じ道
- 着いてからさらに350ミリ秒待つ必要はない（動きそのものが「止まるまで待つ」の代わりになる）。**着いたらすぐ受信を始める**ことを推奨

## 4. Wi-Fi・USBの再生への影響

| 項目 | 影響 |
| --- | --- |
| 通る処理 | 「局→雑音→局」は、MANUALで局をまたぐときと同じ処理。復号のタスク、`stopStream()`、USBの `STOP`→`TUNE`→`RDSYNC` は変えない（USBのシミュレーションでも「STOP→TUNE」は確かめ済み） |
| 局を開く回数 | 今のAUTOは350ミリ秒止まるたびに開く。案では**着いたときだけ**開く。続けて回したときに途中の局は開かない（中継への要求も減る） |
| 描画が増えることの影響 | 動いている間は**局の音声を受信していない**（雑音だけ）ので、描画で受信のバッファーが減る心配はない。描画は `loop()`（コア1）、雑音は復号のタスク（コア0） |
| USBのリンク | 動いている間は中継は止まっている。`usbLink.service()` は `loop()` で今までどおり回る（1こまの描画は約1.5ミリ秒【推定】） |

## 5. 動いている間にノブを回したとき（案）

| 入力 | 動き |
| --- | --- |
| 同じ向き | 目標を**さらに1局先**にする（回した分だけ。ただし一周を超えないよう最大で「局数−1」局先まで）。速さは同じで、途中の局では止まらず、受信もしない |
| 逆の向き | 目標を、**今の位置から逆向きに最も近い局**にする（ふつうは出てきたばかりの局）。同じ速さで向きを変えて戻る。表示は跳ばない |
| A（モード切替） | その場で止める。MANUALになり、局の間なら雑音のまま（今のMANUALと同じ） |
| L（Location）、W（Wi-Fi） | 動きをやめる（今までどおり画面を移る） |
| 押して回す（音量）、押す（ミュート） | 動きに影響しない |

急な向きの変更も「目標の局を替えるだけ」で、雑音は鳴り続け、局を開くのは最後に止まった1回だけなので、表示も音も乱れない。

## 6. 描画の負荷と容量

| 項目 | 見込み |
| --- | --- |
| 1こま（1段＝2ピクセル）の描画 | U6の実測で最大274回・1,787画素（約1.5ミリ秒【推定】） |
| 1秒あたり（50こま） | 約75ミリ秒（`loop()` のコア1の約7.5%）。動いている間だけ |
| 1局の移動 | 局の間18〜23段：0.36〜0.46秒（100 px/秒のとき） |
| フラッシュ | 約0.4〜0.7 KB【推測】（目標と速さの管理、追加入力、描く間隔）。U7の残り2,432 B → 約1.7〜2.0 KB |
| RAM | 数十バイト |

## 7. 推奨する速さ

**毎秒50段＝100ピクセル（20ミリ秒ごとに1段＝2ピクセル）**を推奨する。

- 1こまで1段（MANUALの1目盛りと同じ2ピクセル）なので、目盛りが「回したとき」と同じ細かさで流れ、跳びが見えない
- 局から局まで約0.4秒で、待たされる感じは少ない（今のAUTOの「350ミリ秒止まってから受信」とほぼ同じ時間で、その間に流れが見える）
- 1秒あたりの描画は約75ミリ秒で、その間は局の受信をしていないので、受信の安定性には影響しない
- 速すぎる場合（目で追えない）は、30ミリ秒ごとに1段（約67 px/秒、1局0.6秒）に下げられる。実機で決める

## 8. 作者に決めていただきたいこと

1. 速さ：毎秒100ピクセルでよいか（実機で調整できるよう、定数1つにする）
2. 着いたらすぐ受信を始めるか（推奨）、MANUALと同じく350ミリ秒待つか
3. 動いている間の表示：状態の行を「TUNING...」にし、局名の行は空ける（推奨。今のコードのままだと局の間では「NO STATION」になる）
4. 同じ向きの追加入力の上限（推奨：局数−1）
5. 版：U7に加えるか、U8にするか
